
## 1.4. Схема реляционной базы данных задачи

### 1.4.1. Правила перехода к схеме отношений

При преобразовании ER-модели в схему реляционной базы данных применены правила:

1. каждый набор объектов становится таблицей, сущность — строкой, атрибут — столбцом;
2. ключ набора объектов становится первичным ключом таблицы;
3. связь 1:М реализуется переносом первичного ключа таблицы со стороны «один» в таблицу со стороны «многие» в качестве внешнего ключа;
4. связь М:М реализуется через связующую таблицу с составным первичным ключом.

В результате получено **восемь таблиц**, одна из которых (FILM_ZHANR) является связующей.

### 1.4.4. Вычисляемые столбцы и представления

В структуре базы данных предусмотрены вычисляемые столбцы, значения которых не вводятся пользователем, а рассчитываются СУБД:

- **ZAL.vsego_mest** — вместимость зала, равная произведению числа рядов на число мест в ряду;
- **BILET.itogovaya_cena** — итоговая стоимость билета, равная цене без скидки, умноженной на (1 − скидка / 100).

Для отчётности созданы представления (виртуальные таблицы): **v_raspisanie** — расписание сеансов с названиями фильма и зала; **v_seans_svodka** — количество проданных билетов, выручка и процент заполненности зала по каждому сеансу.

### 1.4.5. Нормализация схемы

**1НФ.** Все поля таблиц атомарны, повторяющихся групп нет. Множественные сведения вынесены в отдельные таблицы: жанры фильма — в FILM_ZHANR, сеансы — в SEANS, билеты — в BILET. Фамилия и имя хранятся в отдельных полях.

**2НФ.** Все неключевые поля зависят от полного первичного ключа. Проверка существенна для связующей таблицы FILM_ZHANR: она состоит только из ключевых полей, поэтому частичных зависимостей в ней нет. Название жанра в эту таблицу не включено, так как зависело бы только от id_zhanra.

**3НФ.** Транзитивные зависимости отсутствуют: в таблице SEANS не хранятся название и длительность фильма — они зависели бы от id_filma и находятся в таблице FILM; в таблице SEANS не хранится вместимость зала — она вычисляется в таблице ZAL; в таблице BILET не дублируются фамилия клиента и фамилия кассира, хранятся только их коды.

Отдельно следует пояснить поля **cena_bez_skidki** и **skidka_procent** в таблице BILET. На первый взгляд они дублируют базовую цену сеанса и скидку клиента, однако это не нарушение нормальных форм: цена и скидка фиксируются в момент продажи и не должны изменяться задним числом при изменении цены сеанса или размера скидки клиента. Такое решение отражает требование предметной области.

Все восемь таблиц находятся в третьей нормальной форме.

### 1.4.6. Правила целостности данных

| Правило предметной области | Реализация в базе данных |
|---|---|
| Каждая запись однозначно определяется | первичный ключ в каждой таблице |
| Сеанс ссылается на существующие фильм и зал | внешние ключи SEANS.id_filma, SEANS.id_zala |
| В одном зале в одно время только один сеанс | UNIQUE (id_zala, data_seansa, vremya_nachala) |
| Одно место на сеанс продаётся один раз | UNIQUE (id_seansa, ryad, mesto) |
| Жанр не повторяется у фильма дважды | составной первичный ключ FILM_ZHANR |
| Длительность фильма и цена положительны | CHECK (dlitelnost_min > 0), CHECK (bazovaya_cena > 0) |
| Скидка не превышает 50 % | CHECK (skidka_procent BETWEEN 0 AND 50) |
| Возрастной рейтинг из перечня | CHECK (vozrastnoy_reyting IN ('0+','6+','12+','16+','18+')) |
| Статус билета из перечня | CHECK (status IN ('продан','забронирован','возвращён')) |
| Нельзя удалить фильм, на который есть сеансы | ON DELETE RESTRICT |

### 1.4.7. Реализация структуры базы данных

В качестве СУБД выбрана SQLite: база данных хранится в одном файле `kinoteatr.db` рядом с программой, не требует установки сервера и настройки, что удобно для настольного приложения.

Скрипт создания таблиц `kino_schema.sql` содержит описания всех восьми таблиц с первичными и внешними ключами, ограничениями CHECK и UNIQUE, вычисляемыми столбцами (`GENERATED ALWAYS AS`), индексами по полям связей и двумя представлениями.
